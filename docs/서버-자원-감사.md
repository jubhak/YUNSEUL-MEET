# 서버 자원(CUDA / VRAM / CPU) 감사 및 딥페이크 부하 분배

측정일: 2026-09-30 · 측정 장비: RTX 5070 Ti (16GB) / Ryzen 9 9950X3D (16C/32T) / Windows 11
측정 도구: `tests/bench_faceswap_gpu.py` (합성 클라이언트), `tests/e2e_deepfake_browser.js` (실제 브라우저)

## 1. 구조

```
참가자 웹캠 → (브라우저) 워커 스레드에서 리사이즈+JPEG → WS /face-swap-ws (Node 프록시)
           → Python aiohttp 워커 (InsightFace + inswapper, ONNX CUDA)
           → 합성된 JPEG → 참가자 → SFU(mediasoup) → 호스트 화면
```

- 딥페이크는 GPU 1장을 모든 참가자가 공유합니다. 참가자 수가 늘면 **참가자당 fps 가 줄어드는 것이 정상**이며,
  워커가 `throttle` 메시지(fps / max_w)를 내려 클라이언트가 스스로 속도를 맞춥니다.
- 연결당 "가장 최신 프레임 1개"만 대기시키므로(오래된 프레임은 `drop`), 과부하일 때 **지연이 누적되지 않고 fps 만 낮아집니다.**
- mediasoup 은 워커 프로세스 수를 `MEDIASOUP_WORKERS`(기본 자동, CPU 코어 기반)로 정하며,
  딥페이크(GPU)와 CPU 코어 경쟁이 없도록 영상 릴레이는 CPU, 딥페이크는 GPU 로 분리됩니다.

## 2. 측정 결과 (이번 세션, 12클라이언트 = 목표 15fps 요청)

| 설정 | 총 처리량 | 클라이언트당 | GPU 사용률(평균/최대) | VRAM 최대 | 지연 p50 |
|---|---|---|---|---|---|
| **기본(FACE_SWAP_WORKERS=0, 프로세스 1개 + 자동 동시성 4)** | **115 fps** | 9.6 fps | 77% / 92% | 7.1 GB | 105 ms |
| 멀티프로세스 4개 (`FACE_SWAP_WORKERS=4`) | 83 fps | 6.9 fps | 88% / 92% | 7.8~8.6 GB | 143 ms |
| 멀티프로세스 6개 (`FACE_SWAP_WORKERS=6`) | 83.5 fps | 7.0 fps | 87% / 93% | 9.4 GB | 143 ms |
| 기본, 4클라이언트 | 60 fps | 15.0 fps (요청치 100%) | 41% / 51% | 7.1 GB | 39 ms |
| 멀티프로세스 4개, 1클라이언트 | 15 fps | 15.0 fps | 16% / 55% | 7.8 GB | 21 ms |

원래 코드(기준선)는 12클라이언트에서 총 77 fps · 클라이언트당 6.4 fps · GPU 66% · VRAM 3.2 GB 였습니다.
→ 총 처리량 +49%, VRAM 은 GPU 16GB 중 약 7GB 까지 적극 사용하도록 변경했습니다.

### 해석
- **결론: 멀티프로세스 분할은 오히려 느립니다.** 프로세스가 늘면 CUDA 컨텍스트 전환/메모리 복사가 늘어
  총 처리량이 떨어졌습니다. 그래서 기본값은 "프로세스 1개 + 내부 GPU 세션 4개 + CPU 합성(paste) 병렬"로 유지합니다.
  (`FACE_SWAP_WORKERS` 는 GPU 가 여러 장이거나 VRAM 이 매우 클 때만 시험해 보세요.)
- 12명 동시일 때 GPU 사용률이 77~92% 이므로 **이 GPU 의 한계(약 115 fps)에 근접**해 있습니다.
  이 이상은 GPU 성능(더 좋은 GPU, TensorRT 등) 없이는 늘리기 어렵습니다.
  참가자가 4명 이하이면 모두 15 fps 를 여유 있게 받습니다.
- 12명 이상에서 참가자당 fps 는 `총 처리량 ÷ 인원`으로 정해집니다 (12명 ≈ 9~10 fps, 20명 ≈ 5~6 fps).
  이때도 프레임이 밀리지 않고(지연 ≈ 100 ms 유지) 부드러움만 낮아집니다.

## 3. 실제 브라우저 종단 테스트 (`tests/e2e_deepfake_browser.js 3 8`)

| 항목 | 값 |
|---|---|
| 참가자(뷰어) 3명, 딥페이크 켬 | 각 **22.5 ~ 23.5 fps** 스왑 응답, 드롭 0 |
| 숨겨진(백그라운드) 탭 참가자 | 수정 전 ~1 fps → 수정 후 **~23 fps** |
| 호스트가 수신한 카메라 스트림 | 3개 모두 **19 ~ 20.6 fps**, 480x270, 프리즈 0 |
| RTT / 서버 처리 | 약 20 ms / 약 18 ms |

### 숨겨진 탭에서 1fps 로 얼어붙던 원인 (수정됨)
메인 스레드의 canvas JPEG 인코딩(`convertToBlob`/`toBlob`)이 백그라운드 탭에서는 브라우저의 idle 스케줄러에 묶여
프레임당 약 1초씩 지연됐습니다. 이제 `createImageBitmap` 으로 프레임을 잡아 **전용 Web Worker 에서 리사이즈 + JPEG 인코딩**을 수행하고
(미지원 브라우저는 기존 방식으로 자동 폴백), 렌더/송신 타이머도 스로틀되지 않는 Worker 타이머를 사용합니다.
부수 효과로 메인 스레드 부하가 줄어 화면이 더 부드럽습니다.

## 4. CPU / 기타 자원

- Python 워커: 프로세스당 OMP 스레드 2개(`FACE_SWAP_OMP_THREADS`), 얼굴 감지는 5프레임마다(`FACE_SWAP_DETECT_EVERY`)
  실행하고 사이에는 추적값 재사용 → CPU 사용을 줄이면서 GPU 는 합성에 집중.
- CPU 합성(paste-back)은 별도 스레드 풀에서 병렬 실행되어 GPU 추론과 겹칩니다(`FACE_SWAP_CPU_PASTE=1`).
- mediasoup: 영상 릴레이는 CPU 로 처리되며 참가자 12명 규모에서는 코어 몇 개 수준입니다.
- VRAM: 모델 상주분(약 3GB) + 세션별 작업 버퍼. 16GB 카드 기준 7~9GB 사용, 여유 약 7GB.
  VRAM 이 적은 카드는 `FACE_SWAP_CONCURRENCY=2` 등으로 낮추세요.

## 5. 모니터링

- 워커 `GET http://127.0.0.1:<FACE_SWAP_PORT>/stats` : `capacity_fps`, `throughput_fps`, GPU 사용률/VRAM/온도/전력, 지연 p50/p90.
- 참가자 화면의 스왑 통계(`swapStats`, RTT, 처리 시간)는 `window.__ymDebug` 로 확인 가능합니다.

## 6. 호스트 직송(face-feed) — stress_test.html 과 같은 경로로 호스트에 표시 (추가 개선)

기존: 참가자 PC 가 딥페이크 결과를 받아 canvas → VP8 재인코딩(170~350kbps) → SFU → 호스트 디코드.
개선: 서버가 GPU 워커 결과 JPEG 를 **호스트에게 곧바로도 전달**(`/face-feed`, 호스트 토큰 인증)하고,
호스트는 참가자별 canvas 에 그려 화면(그리드/PIP)에 표시합니다. (참가자 재인코딩·SFU·지터버퍼 구간이 빠짐)

- 참가자 → 서버 경로(`/face-swap-ws`)는 기존과 동일 프로토콜이며, Node 릴레이(`server/face-relay.js`)가 워커로 중계하면서 결과를 호스트 feed 로 복제합니다.
- SFU 경로는 그대로 유지됩니다. 직송이 0.9초 이상 끊기거나(딥페이크 끔/네트워크) 카메라가 꺼지면 **자동으로 SFU 영상으로 복귀**, 다시 프레임이 오면 직송으로 복귀합니다(브라우저 e2e 로 검증).
- 참가자 송신 해상도는 인원과 무관하게 서버 허용 최대(기본 640px)까지 올렸습니다(과부하 시 서버 throttle 이 자동 축소).
- 끄는 방법: 서버 `FACE_FEED=0`(직송만 끔) / `FACE_RELAY=0`(릴레이 자체를 끄고 기존 raw 프록시 사용) / 호스트 URL `?feed=0`.
- 워커 permessage-deflate 를 껐습니다(JPEG 은 압축 불가, CPU 낭비).
- **참가자에게 결과 JPEG 를 돌려주지 않습니다(기본 `FACE_CLIENT_RETURN=auto`).** 호스트 직송으로 실제 전달된 프레임은
  참가자에게 13바이트 ack(응답 헤더만)만 보냅니다. 참가자는 ack 로 전송 슬롯/RTT 를 갱신하고 다음 프레임을 보냅니다(클라이언트 수정 없음).
  - 호스트가 그 프레임을 못 받은 경우(호스트 미접속, 느린 호스트로 드롭, `?feed=0`, 방 조회 실패)는 전체 JPEG 를 돌려줘서 SFU 폴백 영상이 유지됩니다.
  - 호스트 본인의 카메라 프레임은 호스트가 `room.viewers` 에 없으므로 항상 전체가 돌아옵니다(기존과 동일).
  - 직송이 정상이어도 `FACE_CLIENT_KEEPWARM_MS`(기본 2000ms)마다 1장은 전체를 돌려 참가자 쪽 canvas(폴백 영상)를 신선하게 유지합니다. 0 이면 끔.
  - 예전처럼 항상 돌려주려면 `FACE_CLIENT_RETURN=always`. 절약량은 `face-relay` stats 의 `clientAcked` / `clientReturned` 로 확인합니다.
  - 효과: 서버 송신과 참가자 다운로드가 줄어듭니다(GPU 처리량 자체는 변하지 않음).
- **호스트 보고 기반 판정**: 서버는 "전송 성공"만으로 ack 로 줄이지 않습니다. 호스트가 직송 WebSocket 으로 0.4초마다
  `{t:'live', ids:[…]}`(지금 직송을 화면에 그리고 있는 참가자)를 보고하고, 그 보고가 최근 1.2초(`FACE_FEED_LIVE_TTL_MS`) 안일 때만
  ack 로 줄입니다. 보고가 없으면(구버전 호스트, 호스트 탭이 백그라운드라 타이머가 느려진 경우 포함) 자동으로 전체 JPEG 를 돌려줍니다.
- **SFU 카메라 송출(VP8) 절감**: 직송이 2초 이상 연속으로 정상이면 서버가 참가자의 `/face-swap-ws` 로
  `{type:'feed', live:true}` 를 보내고(4초마다 재통지), 참가자는 SFU 카메라 송출을 **3fps / 100kbps** 로 낮춥니다.
  참가자 업로드와 호스트 VP8 디코드(참가자 수 × fps)가 크게 줄어듭니다. producer/consumer 를 pause 하지 않으므로
  복구 때 키프레임 공백이 없습니다.
  - 직송 이상(보고 중단, 호스트 연결 종료, 전송 실패) 시 서버가 즉시 `live:false` 를 보내 원래 프로파일로 복원합니다.
  - 안전장치: 서버는 프레임이 3초 끊기면 자동 해제, 참가자는 통지가 8초 없거나 스왑 연결이 끊기거나 실물 모드로 돌아가면 스스로 복원합니다.
  - 끄는 방법: 서버 `FACE_SFU_SAVE=0`. (`FACE_CLIENT_RETURN=always` 이면 함께 꺼집니다.)
  - 서버/호스트/참가자 버전이 섞여도 안전합니다(구버전은 새 메시지를 무시하거나 보고를 하지 않아 기존 동작).
- 추가 GPU 워커(선택): `FACE_SWAP_EXTRA_WORKERS=N` (또는 `FACE_SWAP_PORTS=8765,8766,…`) 를 주면 릴레이가 접속 수가 적은 워커로 분배합니다.
  이 PC(RTX 5070 Ti 1장)에서는 12명 기준 115 → 120 fps (+4%) 이고 VRAM 이 7GB → 13.5GB 로 늘어, **기본은 꺼 둡니다**(GPU 여러 장일 때 유리).

브라우저 e2e (`tests/e2e_deepfake_browser.js`, 헤드리스 Chrome 참가자 + 호스트, 가짜 카메라):

| 참가자 수 | 호스트 직송 수신 fps (참가자당) | 해상도 | 서버 처리 |
|---|---|---|---|
| 3 | 23 ~ 29 | 640x360 | 14~18 ms |
| 8 | 약 19 | 512x288 | 17~34 ms |
| 12 | 약 13.4 (총 160 fps) | 512x288 | 17~32 ms |

(참고: 기존 SFU 경로는 같은 조건에서 참가자당 약 20fps, 480x270, 재인코딩 화질)

## 6-1. 20명 규모 개선 (AIMD · 동시 요청 제한 · PLI · 화면 비트레이트) — 측정 결과

`node tests/e2e_deepfake_browser.js 20 20` (참가자 20명 전원 딥페이크, 헤드리스 Chrome, 이 PC GPU 1대 기준)

| 항목 | 개선 전 | 개선 후 |
|---|---|---|
| 참가자당 딥페이크 fps | 8.5 | 8.6 (GPU 총 처리량 ≈ 172 fps 로 동일) |
| 서버 왕복 지연 (참가자 RTT) | 약 230 ms | 약 110 ms |
| SFU 카메라 업로드 | 약 8 fps × 20 (VP8) | 3 fps × 100 kbps × 20 (직송이 살아있는 동안) |

- **동시 요청 1장 제한 (`js/virtual-avatar-manager.js`)**: 서버가 알려준 접속자 수가 8명 이상이면 참가자당 동시 요청을 2 → 1 로 줄입니다.
  GPU 가 처리량을 정하므로 fps 는 그대로이고, 큐에 쌓이는 프레임이 절반이 되어 지연이 절반이 됩니다(리틀의 법칙).
- **AIMD 요청 fps (`server/face_swap_worker.py`)**: 예전 "인원별 하한 fps 고정"(20명 × 8fps = 160fps 요구)을 없애고,
  대기 초과 폐기·덮어쓰기 폐기가 늘면 요청 fps 를 줄이고(×0.9, 실측 처리량/인원 이하) 여유가 있으면 천천히 올립니다(+0.5/2초).
  `FACE_SWAP_AIMD=0` 으로 예전 방식 복귀, `FACE_SWAP_MIN_FPS`(기본 4) 로 안전 하한 조정. 로그에 `[AIMD] n=… fps=…` 가 2초마다 남습니다.
  이 PC 의 20명 테스트에서는 클라이언트 쪽 1장 제한이 먼저 부하를 흡수해 AIMD 가 작동할 일이 없었습니다(superseded=0, stale=0). 회선이 느려 응답이 늦는 실환경에서 안전망으로 동작합니다.
- **처리량 측정 버그**: `measured_throughput_fps` 가 이벤트 512개 상한 때문에 128fps 를 넘게 측정하지 못했습니다 → 4096 으로 확대(실측 172fps 확인).
- **PLI 스로틀 (`server/sfu.js`)**: 닫힌 producer 의 기록이 지워지지 않아(누수) 20명 방에서는 1:1 로 호스트만 보는 참가자 카메라의 키프레임 복구도 7초 넘게 막힐 수 있었습니다.
  producer/consumer 종료 시 정리하고, 간격을 "그 producer 를 보는 consumer 수"에 비례하게 바꿨습니다(1명이면 1.5초).
- **호스트 화면 비트레이트 (`js/webrtc/sfu-client.js`, `host-publisher.js`)**: 호스트 화면은 시청자 수만큼 복제되어 서버 상향 회선을 가장 많이 쓰는 스트림입니다.
  9명 이상이면 `36 Mbps / 인원` (0.8~3 Mbps) 상한을 걸고(20명 → 1.8 Mbps), 시간계층 L1T3 를 켜서 느린 시청자에게는 프레임만 솎아 보내게 했습니다.
  L1T3 를 못 받는 환경이면 자동으로 단일 계층으로 폴백합니다. 검증: `node tests/e2e_display_egress.js 20 10` (시청자 20명 전원 수신, 상한 1.8 Mbps 적용).
- **TURN (선택, C-1)**: `.env` 에 `TURN_URLS`, `TURN_USERNAME`, `TURN_CREDENTIAL` 을 넣으면 SFU 가 클라이언트에 TURN 정보를 내려줍니다. 설정이 없으면 동작 변화 없음.
- **TensorRT A/B**: `FACE_SWAP_TRT=1` 은 이 PC 에 TensorRT 라이브러리가 없어 CUDA 로 폴백되므로(로그: `Please install TensorRT libraries`) 비교가 성립하지 않았습니다. 설치 후 같은 명령으로 재측정하세요.
- **실측 확인**: 부팅 로그 `SFU ICE IPs: 118.217.198.27, 192.168.0.77` — 공인 IP 가 올바르게 광고됩니다.

## 6-2. 딥페이크 1프레임 비용 · 입장 제어 · 업로드 품질 자동 조절

**비용 실측** (`tests/profile_faceswap_stages.py`, `tests/tune_onnx_batch_graph.py`, `tests/bench_faceswap_gpu.py`)
- 프레임 1장 = JPEG 디코드 0.25ms + 얼굴검출 6.2ms(5프레임마다 1회) + inswapper ONNX **7.6~7.9ms** + 붙여넣기 1.9ms + 인코딩 0.24ms ≈ 12.5ms (스레드 1개 = 최대 80fps).
- inswapper 모델은 입력이 batch=1 로 고정되어 여러 얼굴을 한 번에 묶어 처리할 수 없다(batch=2 는 INVALID_ARGUMENT). 스레드 4개로 겹쳐도 GPU 가 79~89% 까지 차서 총 **약 120~170 fps** 에서 포화.
- 즉 "한 장당 비용"은 작지만 **총량이 고정**이라 참가자당 fps ≈ 총량 ÷ 인원 (12명 ≈ 10~13fps, 20명 ≈ 6~9fps). 화질(해상도)은 인원과 무관하게 유지되고 줄어드는 것은 fps 뿐이다.
- `stress_test.html` 이 12개에서 잘 도는 것도 같은 이유(12 × 13fps ≈ 160fps ≈ 총량). 20개로 늘리면 총량은 그대로이고 개당 fps 만 8~9 로 내려간다.

**입장 제어 (`server/face_swap_worker.py`)**: 딥페이크를 (다시) 적용할 때마다(WS 접속, `set_source`) "추가 시 참가자당 fps = 처리량×0.9 ÷ (활성 인원+1)" 를 계산해 `FACE_SWAP_MIN_ADMIT_FPS`(기본 6) 미만이면 `{type:'busy'}` 를 보내고 거절한다.
- 처리량 = max(실측 최고치, `FACE_SWAP_CAPACITY_FPS`(기본 150)). 이미 과부하 신호(대기 초과 폐기)가 있으면 "실측 처리량 ÷ 인원" 으로 더 엄격히 판단.
- 활성 = 최근 6초 안에 프레임을 보낸 참가자(또는 방금 승인된 참가자). 호스트(`prio=host`)는 거절하지 않지만 인원에는 포함된다.
- `FACE_SWAP_MAX_CLIENTS` 로 절대 상한을 줄 수 있고 `FACE_SWAP_ADMISSION=0` 이면 끈다. `/stats` 의 `admission` 에 승인/거절 누적이 나온다. 검증: `node tests/test_face_admission.js`.
- 참가자 화면: 실물 얼굴이 나가지 않도록 카메라를 끄고 "서버 하드웨어 상황에 따라 더 이상 딥페이크를 적용할 수 없습니다" 안내를 띄운다. 다시 얼굴을 고르면 그때 다시 확인한다.
- 이 PC 기준 기본값이면 최대 약 22명(150×0.9÷6).

**업로드 품질 자동 조절 (`js/virtual-avatar-manager.js`)**: 순수 네트워크 왕복(RTT − 서버 처리시간)과 송신 버퍼 적체를 보고 단계를 조절한다.
L0 기본(≤640px) → L1 ≤480px/q0.62 → L2 ≤384px/q0.55/15fps → L3 320px/q0.5/10fps. 2초마다 평가, 내릴 때는 3초 간격, 올릴 때는 안정 12초 후 한 단계씩.
검증: `SLOW_MS=300 SLOW_FOR_S=16 node tests/e2e_deepfake_browser.js 2 26` (L1→L2→L3 로 내려가고, 회복되면 올라옴).

## 6-3. 시청자 화면에서 참가자 영상이 뚝뚝 끊기던 문제 (호스트 화면 공유 인코딩)

- 시청자는 참가자 카메라를 직접 받지 않고 **호스트의 화면 공유(display)** 를 받는다. 호스트 화면에는 참가자 타일이 움직이고, 호스트는 로컬 렌더링이라 부드럽지만 시청자는 이 화면의 **VP8 인코딩 결과**를 본다.
- 원인: 화면 공유가 'detail' + `maintain-resolution`(글씨 우선)이라, 움직이는 타일이 많은 1920x1080 화면을 2.3~2.5Mbps 에 맞추려고 **해상도는 지키고 프레임을 버린다 → 약 4fps**. 타일마다 갱신 시점이 달라 "제각각 끊겨" 보인다. (예전 설정에서도 4.1fps, 인원별 상한 도입 후 3.1fps 로 더 악화, L1T3 는 freeze 증가)
- 수정: 호스트 화면에 참가자 영상 타일이 있으면(`host.js` 2초 주기 확인, 끌 때는 15초 지연) 'motion' + `maintain-framerate`(프레임 우선)로 전환 (`sfu-client.setDisplayMotion`). 타일이 없으면(PPT/문서) 기존처럼 글씨 우선.
  L1T3 는 기본 끔(`_useTemporalLayers`). 화면 송출 상한 예산은 36 → 50Mbps (20명 → 시청자당 2.5Mbps).
- 측정 (`VARIANT=… node tests/e2e_display_motion.js 20 12`, 20타일이 움직이는 1080p 가상 화면, 시청자 20명):

| 설정 | 호스트 인코딩 | 시청자 수신 | freeze |
|---|---|---|---|
| 예전(detail, 상한 없음) | 4.1fps 1920x1080 | 4.1fps | 0 |
| 인원별 상한 + detail | 4.3fps 1920x1080 | 4.3fps | 0 |
| **지금(motion + 상한)** | **29.9fps 640x360, 2.4Mbps** | **30.1fps** | **0** |

- 트레이드오프: 프레임 우선이면 대역폭이 부족할 때 해상도가 자동으로 내려간다(위 가상 화면은 고엔트로피 최악 조건). 서버 상향 회선(약 80Mbps) 기준 20명 × 2.5Mbps ≈ 50Mbps 를 화면 송출에 쓴다.

## 7. 한계 / 미검증

- 위 수치는 이 PC 한 대의 측정값입니다. GPU 종류에 따라 크게 달라집니다.
- 브라우저 종단 테스트는 가짜 카메라(Chrome fake device)와 헤드리스 Chrome 3~4탭으로 수행했습니다.
  실제 12명이 동시에 접속하는 실환경 부하(업링크 대역폭, 모바일 기기 성능)는 검증하지 못했습니다.
- 호스트 직송은 참가자 12명 기준 호스트 쪽 다운로드가 약 25~30 Mbps(JPEG) 입니다. 호스트가 서버와 같은 PC/LAN 이면 문제 없지만,
  호스트 회선이 느리면 서버가 송신 버퍼(512KB)가 차는 즉시 프레임을 버려 fps 만 낮아지고, 0.9초 이상 끊기면 SFU 영상으로 자동 복귀합니다.
  회선이 매우 느린 원격 호스트는 URL 에 `?feed=0` 을 붙여 SFU 만 쓰도록 할 수 있습니다.
